## 1. Definition of done

On a clean laptop, `docker compose up` followed by `docker compose run --rm seed` brings up the whole system. In it, the team can show the following live:

1. Log in as HQ admin, branch manager and cashier. Each sees only their own menus and branches.
2. Make a POS sale. Within seconds, stock goes down and "today so far" goes up. Retrying the same sale creates no duplicate.
3. Refund a sale. Stock goes back up and the revenue figure drops.
4. Daily, monthly, cross-branch and company reports, based on 6 months of seeded history.
5. A forecast vs actual chart, with the forecast's WAPE next to a naive baseline.
6. A reorder suggestion with an LLM "Why?" explanation, approved, then turned into a purchase order, then received, after which stock goes up.
7. The LLM morning briefing on the branch and HQ dashboards.
8. Failure demos: stop Inventory, sell, restart it, and stock catches up (lag visible in `kafka-ui`). Stop Ollama and the briefing falls back to a template.
9. The Order service's DB user is refused access to `inventory_db`.

Anything not on this list is a bonus.

## 3. Ground rules

**Git**
- One GitHub repo, `main` protected. Work on short branches (`m3/pos-order-endpoint`) and merge through a PR with one reviewer.
- **Merge at least once a day.** `main` must always pass `docker compose up` plus the smoke test ([§13](#13-testing)).
- A broken `main` is everyone's first job.

**Daily**
- A 15-minute stand-up (in person or chat): done yesterday, doing today, blocked on.
- The phase exit checks in this plan are the milestones. If a phase slips by more than half a day, cut scope from the "deferred" list in design doc §13.2. Don't push the schedule back.

**Conventions** (used by every service and the front end)

| Thing | Convention |
|---|---|
| JSON field names | `snake_case` |
| Money | Decimal **string** with 2 places in JSON (`"3.40"`); `DecimalField(12, 2)` in the DB. Never floats. |
| Timestamps | ISO 8601 with offset, `Asia/Phnom_Penh` (`2026-11-26T14:03:22+07:00`). Store as `timestamptz`. |
| Dates | `YYYY-MM-DD`. `sale_date` is the local date. |
| IDs | Branches `BR-01`…`BR-05`. SKUs as uppercase codes (`COKE-330`). Everything else UUIDv4. `order_id` is generated by the browser with `crypto.randomUUID()`. |
| API errors | `{"error": {"code": "PRICE_UNAVAILABLE", "message": "...", "details": {}}}` with a fitting HTTP status |
| Pagination | `?page=&page_size=` → `{"results": [], "count": n}` (DRF `PageNumberPagination`) |
| Gateway paths | `/api/<service>/...` with the service name (`/api/admin`, `/api/catalog`, `/api/inventory`, `/api/order`, `/api/analytics`). Nginx strips the prefix, so services expose `/branches`, not `/api/admin/branches`. |
| Request ID | Gateway sets `X-Request-ID`. Services log it and copy it into the event envelope as `correlation_id`. |

**Ports** (host side, dev only except 8080)

| Port | What |
|---|---|
| 8080 | Gateway (web app + APIs). The only port used in the demo. |
| 8081 | `kafka-ui` |
| 5173 | Vite dev server (front-end development) |
| 5432 | PostgreSQL (dev debugging) |
| 9094 | Kafka, for scripts run on the host (`localhost:9094`) |
| 11434 | Ollama on the host |

```

├── README.md                    # how to run, demo accounts, troubleshooting

│   ├── postgres/init.sh         # 5 DBs, 5 users, REVOKE CONNECT FROM PUBLIC

│       ├── events.py            # envelope + publish_event() (writes the outbox)
│       ├── models.py            # Outbox, ProcessedEvent
│       ├── topics.py            # topic catalogue: name, key, cleanup policy
│       ├── create_topics.py     # run by kafka-init: creates every topic + DLQ
│       ├── relay.py             # outbox -> Kafka
│       ├── consumer.py          # @handles registry, idempotent consumer, DLQ
│       ├── management/commands/run_worker.py   # relay + consumer loop
│       ├── settings_base.py     # shared Django settings
│       ├── api.py               # error format, ApiError, pagination
│       ├── health.py            # GET /health view
│       └── contracts/           # one example JSON file per event (frozen on day 1)
├── services/
│   ├── admin/                   # Django project: config/ + apps (accounts, branches)
│   ├── catalog/                 # apps: products, pricing, suppliers
│   ├── inventory/               # apps: stock, purchasing, refs
│   ├── order/                   # apps: sales, caches
│   └── analytics/               # apps: reporting, forecasting, replenishment, insights, jobs
│       (each: requirements.txt, manage.py, config/, <apps>/, tests/)
│   Dockerfile                   # one image recipe for all five (build arg SERVICE)
├── web/                         # Vite + React + TS + Mantine
│   └── src/{api,auth,layouts,features/{hq,branch,pos},components}
├── seed/
│   ├── seed_reference.py        # branches, users, products, prices, suppliers via the REST APIs
│   ├── generate_history.py      # 6 months of synthetic sales
│   └── load_history.py          # bulk insert + run J2/J6 over history
├── scripts/
│   ├── gen_env.py               # creates .env
│   ├── makemigrations.sh        # migrations via the service image
│   ├── smoke.py                 # end-to-end smoke test (§13)
│   └── demo/                    # helpers: stop/start services, poison message
└── docs/                        # design docs, this plan, diagrams, slides
```

**One Dockerfile pattern for all services.** The build context is the repo root, so each image can `pip install ./libs/retail_common` and then its own `requirements.txt`. The same image runs `gunicorn` (web) or `python manage.py run_worker` (worker), chosen by the Compose `command`.

**Python dependencies:** `Django 5`, `djangorestframework`, `psycopg[binary]`, `dj-database-url`, `PyJWT[crypto]`, `confluent-kafka`, `httpx`, `gunicorn`, and `pytest-django` for tests. Analytics also needs `pandas`, `statsmodels` and `APScheduler`.

**Front-end dependencies:** `react`, `react-router-dom`, `@mantine/core` (+ `@mantine/dates`, `@mantine/notifications`), `@tanstack/react-query`, `recharts`, `jwt-decode`.

## 5. Contracts to freeze on day 1

**Monday morning, all four together, about 2 hours.** These are the only things that block people from each other. Once they're agreed, everyone can build in parallel with mocks.

1. **Event payloads.** One example JSON file per event in `libs/retail_common/contracts/`, copied from design doc §6.3 (E1–E8), with the envelope. Any later change needs a PR reviewed by the producer *and* every consumer.
2. **Topic catalogue** (design doc §6.4) as code in `topics.py`.
3. **JWT claims** (design doc §4.1) and the role codes.
4. **REST endpoints the front end needs**, with example responses. Each backend owner writes `services/<svc>/API.md` from design doc §4 and §6.2. M1 builds against these with mock data until the real endpoints land.
5. **Seed identities**: branch IDs `BR-01`…`BR-05`, demo users (`hq@demo.local`, `manager.br01@demo.local`, `cashier.br01@demo.local`, all with password `demo1234`; `hq@demo.local` already exists from the bootstrap), about 200 SKU codes in 10 categories.

**How people work without waiting for each other:**
- **M1** uses mock JSON (a small `mocks/` folder behind a flag in the API client) until each endpoint is live.
- **M4** writes `scripts/fake_orders.py`, which publishes realistic `order.completed` events straight to Kafka, so Analytics can be built before Order exists.
- **M3** can build Order and Inventory models and endpoints in plain Django while M2 finishes `retail_common`, then wire in events.

## 13. Testing

Keep it small and focused on logic the demo depends on. `pytest-django`, run in each service's container.

| Service | Must-have tests |
|---|---|
| retail_common | Outbox row written in the same transaction; consumer skips a duplicate `event_id`; failing handler → DLQ after 3 attempts |
| Catalog | Price rule: a branch price beats `ALL`; latest `valid_from <= date` wins |
| Order | Same `order_id` twice → one order; server ignores client prices; payment ≠ total → 400; missing price → S6 → `PRICE_UNAVAILABLE` on timeout |
| Inventory | SALE movement per line; UNIQUE blocks a double deduction; stock can go negative; E8 twice → one PO |
| Analytics | Fact insert is idempotent; a late event marks its day dirty and J2 recomputes it; reorder formula on a hand-worked example; forecast method chosen by history length; LLM output with an invented number → fallback |

**Smoke test** `scripts/smoke.py` (runs against the gateway, about 30 seconds): log in as cashier → look up an item → `POST /orders` → poll stock until it drops → poll "today so far" until it includes the sale → refund → poll until stock returns. Run it before every merge to `main` from Phase 3 on.

## 15. Risks

| Risk | Likelihood | Mitigation |
|---|---|---|
| Docker Desktop on Windows runs out of memory (about 15 containers + Kafka) | Medium | Set Docker Desktop / WSL2 to at least 8 GB on day 1; cap the Kafka heap; give gunicorn 2 workers per service |
| Integration problems found late | High if we merge rarely | Contracts frozen on day 1; merge daily; smoke test from Phase 3 |
| Kafka learning curve | Medium | M2 builds and tests `retail_common` first; everyone else only calls `publish_event()` and registers handlers |
| Forecast looks bad on synthetic data | Medium | Generate history with a clear weekday pattern; always show it next to the naive baseline |
| Ollama slow or unavailable on demo day | Medium | Generate everything ahead of time; template fallback; demo laptop checked on Dec 3 |
| Schedule slips | High | Cut from the deferred list first, then from "build next"; never cut the failure demo or reconciliation, because they answer the defend-your-design questions |
| Live demo fails | Low to medium | Recorded backup video; seeded data restored with one command |
| A member is unavailable for days | Medium | Every area has a named backup: M2 ↔ M3, M1 ↔ M2, M4 ↔ M3 |
