# Order API

Records POS sales and refunds, and serves the POS screen (design doc §4.4, §6.2 S4/S6/S7, §6.3 E2/E3/E5/E6).

Conventions from `docs/implementation-plan.md` §3 apply to every endpoint:

- Through the gateway the prefix is `/api/order`. The service itself serves `/orders`, with no trailing slash.
- JSON is `snake_case`. Money is a 2-decimal string (`"3.40"`), never a number. Timestamps are ISO 8601 in `Asia/Phnom_Penh`. Dates are `YYYY-MM-DD`.
- Lists are paginated with `?page=&page_size=` and return `{"results": [], "count": n}`.
- Errors are `{"error": {"code": "...", "message": "...", "details": {}}}`.
- External calls send `Authorization: Bearer <JWT>`. A cashier or manager can act only on branches in their token.
- `/internal/*` is not routed by the gateway. Callers send `X-Service-Token`.

The **Phase** column says which phase of the implementation plan builds the endpoint.

| Method and path | Phase | Roles |
|---|---|---|
| `GET /health` | 1 (built) | none |
| `GET /pos/items?branch_id=&barcode=` or `&q=` | 2 (built) | `CASHIER`, `BRANCH_MANAGER` |
| `POST /orders` | 3 | `CASHIER`, `BRANCH_MANAGER` |
| `GET /orders?branch_id=&date=` | 3 | `CASHIER`, `BRANCH_MANAGER` |
| `GET /orders/{order_id}` | 3 | `CASHIER`, `BRANCH_MANAGER` |
| `POST /orders/{order_id}/refund` | 3 | `BRANCH_MANAGER` |
| `GET /internal/sales-summary?date=` | 3 | service token (Analytics J1) |

## GET /pos/items

Served only from `product_cache` and `price_cache`, so the POS keeps selling when Catalog is down. The price follows the rule in design doc §5.2: the latest `valid_from <= today` for the branch, else the latest for `ALL`. The branch comes from the query (`branch_id`) and must be in the token.

`?barcode=4890008100309&branch_id=BR-04` returns one item:

```json
{"sku": "COKE-330", "name": "Coca-Cola 330 ml", "unit_price": "1.70"}
```

`?q=coke&branch_id=BR-04` returns a page of the same objects: `{"results": [...], "count": n}`. `q` matches the name or SKU code (case-insensitive) or the exact barcode.

- `branch_id` and exactly one of `barcode` or `q` are required (`VALIDATION_ERROR` otherwise).
- Only active products are returned. An unknown or discontinued barcode returns 404 `ITEM_NOT_FOUND`.
- `unit_price` is `null` while the item has no price in `price_cache` yet (for example, the product arrived before any `price.changed`).
- The rule lives in `caches/pricing.py`, the same rule as Catalog's `products/pricing.py`.

## POST /orders

```json
{
  "order_id": "6f1c2a3e-…",
  "branch_id": "BR-04",
  "lines": [{"sku": "COKE-330", "qty": 2}, {"sku": "BREAD-WHT", "qty": 1}],
  "payments": [{"method": "CASH", "amount": "4.90"}]
}
```

- `order_id` is generated by the browser with `crypto.randomUUID()` when the cart opens, and reused on retry. A repeat of an existing `order_id` returns the stored order with `200` and creates nothing. A new order returns `201`. An `order_id` that already belongs to another branch returns 409 `ORDER_ID_CONFLICT`.
- The browser sends no prices, and any price it does send is ignored. Order looks up each SKU in `product_cache` and `price_cache`. On a miss it calls Catalog `GET /prices/{sku}?branch_id=` (S6) with a 300 ms timeout. If that fails too, the request is rejected with 422 `PRICE_UNAVAILABLE` and `details.sku`. A discontinued SKU is rejected with 422 `ITEM_NOT_FOUND`.
- `method` is `CASH`, `CARD` or `QR`. The payments must add up to the order total, or the request is rejected with 400 `PAYMENT_MISMATCH`. Its `details` carry the server's numbers, `{"total_amount": "4.90", "lines": [{"sku": "COKE-330", "unit_price": "1.70"}]}`, so a till whose prices went stale can refresh its cart. For cash, send the amount kept, not the amount tendered: change is worked out on the screen.
- `cashier_id` comes from the token, not the body. `channel` is always `POS`.
- A sale at a branch that Order knows is closed is rejected with 409 `BRANCH_CLOSED`. Order keeps a `branch_ref` copy fed by `branch.upserted`, because a closed branch's staff hold valid tokens until they expire.
- The order is saved `COMPLETED`, with `sale_date` set to the date in the business time zone (`Asia/Phnom_Penh`, the only zone a branch may have), in the same transaction as the `order.completed` outbox row.

Response, the order shape that every endpoint below returns too:

```json
{
  "order_id": "6f1c2a3e-…",
  "branch_id": "BR-04",
  "cashier_id": "4c1e…",
  "status": "COMPLETED",
  "total_amount": "4.90",
  "completed_at": "2026-11-26T14:03:22+07:00",
  "sale_date": "2026-11-26",
  "refunded_at": null,
  "refund_date": null,
  "lines": [
    {"line_no": 1, "sku": "COKE-330", "name": "Coca-Cola 330 ml", "unit_price": "1.70", "qty": 2, "line_total": "3.40"},
    {"line_no": 2, "sku": "BREAD-WHT", "name": "White bread", "unit_price": "1.50", "qty": 1, "line_total": "1.50"}
  ],
  "payments": [{"method": "CASH", "amount": "4.90"}]
}
```

`name` and `unit_price` are the snapshots taken at the sale, so an old receipt stays correct after a price change.

## GET /orders and GET /orders/{order_id}

`GET /orders?branch_id=BR-04&date=2026-11-26` lists that branch's orders for the sale date, newest first, paginated. `date` defaults to today.

`GET /orders/{order_id}` returns one order. An order at a branch outside the token returns 403, and an unknown id returns 404 `NOT_FOUND`.

## POST /orders/{order_id}/refund

Refunds the whole order. No body. Sets `status = REFUNDED`, `refunded_at`, `refund_date` (business time zone) and `refunded_by` (from the token), and writes the `order.refunded` outbox row in the same transaction. Returns the order. Refunding an order that is already `REFUNDED` returns it unchanged and publishes nothing, so a retry is safe.

## GET /internal/sales-summary

Reached service to service at `http://order:8000/internal/sales-summary`, with `X-Service-Token`. The gateway does not route it.

`?date=2026-11-26` returns one row per branch with any sale or refund on that date, used by Analytics J1 to detect missing facts:

```json
[{"branch_id": "BR-04", "order_count": 412, "total_amount": "5321.80"}]
```

`order_count` counts the orders sold on the date, refunded later or not. `total_amount` is their total minus the total of the orders refunded on the date. Both match what Analytics reports for the day: sales count on `sale_date`, refunds on `refund_date`.

## Events

| Event | Direction | Phase | Effect |
|---|---|---|---|
| `product.upserted` (E2) | consumes | 2 (built) | Upsert `product_cache` by `sku`. `active` is `status == "ACTIVE"`. A barcode that moved to this SKU is cleared from any other row first. |
| `branch.upserted` (E1) | consumes | 3 | Upsert `branch_ref` (`status`). Used to refuse sales at a closed branch. |
| `price.changed` (E3) | consumes | 2 (built) | Upsert `price_cache` by `(sku, branch_scope, valid_from)`. A price may arrive before its product; the item shows up priced once the product arrives. |
| `order.completed` (E5) | publishes | 3 | On every new order. Payload in design doc §6.3. |
| `order.refunded` (E6) | publishes | 3 | On every refund. Payload in design doc §6.3. |
